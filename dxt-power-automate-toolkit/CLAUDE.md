### Flow JSON schema — modern Power Automate standards (ALWAYS follow these when writing or editing flow JSON)

These rules match what Power Automate's modern designer exports. Deviating from them causes classic-view rendering, import errors, or broken action wiring.

**runAfter status values — UPPERCASE only:**
  ✅ "runAfter": { "ActionName": ["SUCCEEDED"] }
  ✅ Other valid values: "FAILED", "SKIPPED", "TIMEDOUT"
  ❌ Never write: "Succeeded", "Failed", "Skipped", "TimedOut" (mixed case breaks modern runtime)

**Variable types — lowercase only:**
  ✅ "type": "string"  |  "integer"  |  "float"  |  "boolean"  |  "array"  |  "object"
  ❌ Never write: "String", "Integer", "Float", "Boolean", "Array", "Object"

**Trigger schema — always include required array:**
  ✅ "inputs": { "schema": { "type": "object", "properties": {}, "required": [] } }
  ❌ Never omit "required": [] from the trigger schema object

**Definition structure — clean, no extras:**
  ✅ definition keys in order: $schema, contentVersion, parameters, triggers, actions
  ❌ Never add "outputs": {} to the definition — Power Automate does not include it
  ❌ Never add "metadata": { "defaultToEmbeddedConnections": true } to the definition level

**Expression syntax — when the whole value is an expression:**
  ✅ "@outputs('ActionName')"          — direct expression syntax
  ✅ "@variables('VarName')"
  ✅ "some text @{variables('VarName')} more text"  — @{} only for interpolation inside strings
  ❌ Never use "@{outputs('X')}" as the entire value — @{} coerces to string and breaks non-string types

**Workflow metadata XML (customizations.xml <Workflow> entry / json.data.xml) — Active state:**
  ✅ <StateCode>1</StateCode>    (Active — enables new designer and allows running)
  ✅ <StatusCode>2</StatusCode>  (Active)
  ✅ <OnDemand>0</OnDemand>      (0 for Button/manual trigger flows)
  ✅ <IntroducedVersion>1.0.0.0</IntroducedVersion>
  ❌ StateCode 0 / StatusCode 1 = Draft — flow won't appear in modern designer

**Field order inside action objects (match PA export order):**
  type → inputs → runAfter → metadata (operationMetadataId is optional; omit if not propagating from source)

### Expression syntax
Use @{expression} to embed inside a string (interpolation). Use @expression alone when the entire field value is an expression. Safe navigation: use ?['field'] or ?[0] to avoid null errors — e.g. triggerBody()?['Subject'].
Reference:
  - triggerBody()?['field'] — trigger body field (HTTP/manual triggers)
  - triggerOutputs()?['body']?['field'] — full trigger output
  - body('Action_Name')?['field'] — body output from a named action (spaces replaced with _)
  - outputs('Action_Name')?['body']?['field'] — full output from a named action
  - variables('variableName') — read a flow variable
  - items('Apply_to_each_name') — current loop item in Apply to each
  - items('Apply_to_each_name')?['FieldInternalName'] — specific field from current SP list item in loop
  - iterationIndexes('Until_name') — current iteration index in Until loop
  - parameters('paramName') — flow parameter value
  - result('Scope_name') — all action results inside a Scope (used in Catch to inspect Try)
  - result('Try')?[0]?['error']?['message'] — error message from a failed Try scope
  - result('Try')?[0]?['outputs']?['body'] — output body from last action in Try scope
  - actions('Action_Name')?['error']?['message'] — error from a specific named action
  - actions('Action_Name')?['status'] — status of a named action: 'Succeeded', 'Failed', 'Skipped'
  - outputs('HTTP_Action')?['statusCode'] — HTTP status code returned by an HTTP action
  - body('HTTP_Action')?['field'] — parse a field from JSON response body of an HTTP action
  - workflow().tags.flowDisplayName — display name of the current flow (use in error notifications)
  - workflow().tags.environmentName — environment the flow is running in
  - workflow().run.name — current run ID (use to build run history URL)
  - workflow().name — flow ID

### Best practices
  - Naming: Flows use Verb + Subject + Trigger format — 'Send NPS Survey on Case Close', 'Process MM110 Debt Alert'
  - Solutions: Always build flows inside solutions for ALM (export/import across Dev→Test→Prod environments)
  - Variables before loops: Initialize all variables outside and before any Apply to Each to avoid race conditions
  - Try/Catch on every flow: Wrap main logic in a Scope named Try, add Catch scope after with FAILED/TIMEDOUT/SKIPPED run-after. Send Teams/email notification from Catch.
  - Response on every HTTP path: HTTP-triggered flows must respond within 120s on all branches (success AND failure)
  - Pagination on list queries: Enable pagination for SharePoint/SQL list actions to get more than 100 items
  - Filter early: Use OData $filter / Filter Query on connectors rather than filtering in Apply to Each
  - Concurrency carefully: Only enable Apply to Each concurrency when items are truly independent
  - Compose for complex expressions: Use Compose to evaluate and name complex expressions for reuse and debuggability
  - Avoid hardcoded values: Use flow parameters or environment variables for configuration that differs between environments
  - Key Vault for secrets: Always retrieve API keys and passwords from Key Vault connector before HTTP calls — never hardcode in expressions
  - Monitor throttling: SharePoint connector throttles at ~600 requests per minute; SQL Server has its own connection pool limits
  - Child flows for reuse: Extract 3+ repeated action sequences into a child flow
  - Test with Compose: Use a Compose action to test an expression output before using it in a real action
  - UTC timestamps: Power Automate stores all timestamps in UTC — always use convertFromUtc(utcNow(), 'GMT Standard Time') for Irish time display/comparison

## How to read a flow file

Each `Workflows/*.json` file has this shape:

```json
{
  "properties": {
    "connectionReferences": { ... },
    "definition": {
      "triggers": { "TriggerName": { "type": "...", "inputs": { ... } } },
      "actions":  { "ActionName": { "type": "...", "inputs": { ... }, "runAfter": { ... } } }
    }
  }
}
```

Key fields on every action:
- `type` — e.g. `"OpenApiConnection"`, `"If"`, `"Foreach"`, `"Compose"`, `"Http"`
- `runAfter` — dependencies: `{ "PreviousAction": ["Succeeded"] }`. Empty `{}` means run first.
- `inputs` — the action's configuration (connector params, expressions, etc.)

For connector actions (`type: "OpenApiConnection"`):
```json
{
  "type": "OpenApiConnection",
  "inputs": {
    "host": {
      "connectionName": "shared_sharepointonline-1",
      "operationId": "GetItems",
      "apiId": "/providers/Microsoft.PowerApps/apis/shared_sharepointonline"
    },
    "parameters": { "dataset": "https://...", "table": "ListName" }
  },
  "runAfter": {}
}
```

## PA expression syntax

| Goal | Expression |
|------|-----------|
| Action output field | `@{outputs('ActionName')?['body']?['field']}` |
| Full body of action | `@{body('ActionName')}` |
| Variable value | `@{variables('VariableName')}` |
| Trigger body field | `@{triggerBody()?['field']}` |
| Concat strings | `@{concat(variables('A'), ' ', variables('B'))}` |
| Current item in loop | `@{items('ForeachActionName')}` |
| Condition expression | `@equals(variables('Status'), 'Active')` |

Wrap in `@{...}` when the expression is part of a string. Use `@expression` alone (no braces) when the whole value is an expression.

## Tips when helping with these flows

1. **Check `.pa-library.json`** before writing any connector action — it has real JSON snippets from this org's flows with correct `connectionName` values.
2. **Match `connectionName`** from an existing action in the same flow — don't invent connection names.
3. **Action names** must be unique within a flow, PascalCase, no spaces (underscores ok).
4. **`runAfter`** must reference actions that actually exist in the same scope (top-level, or inside the same `Foreach`/`If` branch).
5. For `If` actions: yes-branch actions go in `actions`, no-branch in `else.actions`.
6. For `Foreach` actions: inner actions go in `actions`, and `foreach` is the array expression.

### Tips for writing bot topics

1. Variables: `Topic.VarName` for topic-scoped, `Global.VarName` for cross-topic persistence.
2. Flow inputs use `=VariableName` syntax for dynamic values, plain string for literals.
3. Always declare `outputType` with matching property names to `output.binding` keys.
4. Condition check format: `=Topic.Var = 'full.enum.path.Value'` for closed list choices.
5. Use `kind: GotoAction` with `actionId` to loop back to a previous step.
